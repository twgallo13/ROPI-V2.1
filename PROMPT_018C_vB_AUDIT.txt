Production-Ready IAM Mechanism
───────────────────────────────

Priority 1: Custom Claims (token.role === 'admin')
Priority 2: Metadata Fallback (metadata/admins for staging)

✅ Implementation:

1. Server-Side Admin Management Script
   ────────────────────────────────────
   File: scripts/set-admin-custom-claim.js
   
   Purpose:
   - Set { "role": "admin" } custom claim on Firebase Auth users
   - Production-ready mechanism for admin management
   - Uses Firebase Auth REST API + gcloud access token
   
   Usage:
   $ node scripts/set-admin-custom-claim.js <user-email-or-uid>
   
   Examples:
   $ node scripts/set-admin-custom-claim.js theo@shiekhshoes.org
   $ node scripts/set-admin-custom-claim.js abc123uid456
   
   Requirements:
   - gcloud CLI authenticated: gcloud auth login
   - FIREBASE_API_KEY environment variable (for email lookup)
   
   Features:
   - Lookup UID by email (if email provided)
   - Set custom claims via Firebase Auth REST API
   - Idempotent operation
   - Clear success/error messaging
   - Verification instructions

2. AuthProvider Custom Claims Support
   ────────────────────────────────────
   File: packages/web/src/contexts/AuthProvider.tsx
   
   Key Changes:
   - Added emailVerified state tracking
   - Updated checkAdminStatus to check token claims FIRST
   - Fallback to metadata/admins for staging compatibility
   - Added resendVerificationEmail() helper
   
   Admin Detection Logic:
   ```typescript
   async function checkAdminStatus(user: User | null): Promise<boolean> {
     if (!user) return false;
     
     // PRIORITY 1: Check custom claims (production)
     const tokenResult = await user.getIdTokenResult(true);
     if (tokenResult.claims.role === 'admin') {
       console.log('✅ Admin (via custom claims)');
       return true;
     }
     
     // PRIORITY 2: Fallback to metadata/admins (staging)
     const adminDoc = await getDoc(doc(db, 'metadata', 'admins'));
     const adminEmails = adminDoc.data()?.emails || [];
     return adminEmails.includes(user.email || '');
   }
   ```
   
   Interface Updates:
   - Added emailVerified: boolean
   - Added resendVerificationEmail: () => Promise<void>

3. Firestore Security Rules Custom Claims Support
   ────────────────────────────────────────────────
   File: firestore.rules
   
   New Helper Functions:
   ```
   function isAdmin() {
     return request.auth != null && request.auth.token.role == 'admin';
   }
   
   function isAdminViaMetadata() {
     return request.auth != null 
            && exists(/databases/$(database)/documents/metadata/admins)
            && request.auth.token.email in get(...).data.emails;
   }
   ```
   
   Usage in Rules:
   - Observations: Admin can update/delete any observation
   - Launch Signups: Admin can read all signups, update any signup
   - Combines custom claims check + metadata fallback

═══════════════════════════════════════════════════════════════════════════════

Policy Enforcement
──────────────────

Staging (Soft):
- User sees persistent banner prompting email verification
- Writes ARE allowed (banner-only warning)

Production (Hard):
- User sees persistent banner prompting email verification  
- Writes ARE blocked for write-capable roles (admin, merch, buyer, photographer)
- Clear error message: "Email verification required"

   ────────────────────────────────

   Write Blocking Logic:
   ```typescript
   export function shouldBlockWrites(emailVerified: boolean, isAdmin: boolean): boolean {
     // Staging: Never block writes (soft enforcement)
     if (isStaging()) {
       return false;
     }
     
     // Production: Block writes for write-capable roles if email not verified
     if (isProduction() && isAdmin && !emailVerified) {
       return true;
     }
     
     return false;
   }
   ```
   
   Write-Capable Roles:
   - admin
   - merch
   - buyer
   - photographer

3. Firestore Rules Email Verification Enforcement
   ────────────────────────────────────────────────
   File: firestore.rules
   
   Helper Functions:
   ```
   function requiresEmailVerification() {
     return request.auth != null 
            && (
              request.auth.token.role == 'admin'
              || request.auth.token.role == 'merch'
              || request.auth.token.role == 'buyer'
              || request.auth.token.role == 'photographer'
            );
   }
   
   function isEmailVerified() {
     return request.auth != null && request.auth.token.email_verified == true;
   }
   ```
   
   Applied to Observations:
   ```
   allow create: if request.auth != null
                 && request.resource.data.createdBy.uid == request.auth.uid
                 && (!requiresEmailVerification() || isEmailVerified());
   
   allow update: if request.auth != null
                 && (isAdmin() || resource.data.createdBy.uid == request.auth.uid)
                 && (!requiresEmailVerification() || isEmailVerified());
   
   allow delete: if request.auth != null
                 && (isAdmin() || resource.data.createdBy.uid == request.auth.uid)
                 && (!requiresEmailVerification() || isEmailVerified());
   ```

C. LAUNCH CALENDAR SIGNUP FLOW
═══════════════════════════════════════════════════════════════════════════════

Enhanced Signup Model
──────────────────────

Document ID: ${launchId}_${sha256(email || uid)}
Collection: launchSignups

Fields:
- launchId: string (e.g., "launch_2025_q1_ropi_runner")
- productId: string (Product ID for the launch) *** NEW ***
- userUid?: string (Firebase Auth UID, nullable for public signups)
- email?: string (User's email, required for public mode)
- createdAt: Timestamp
- source: 'aoss-web' | 'public-form'
- status: 'active' | 'cancelled' (default: 'active')

✅ Implementation:

1. Enhanced useLaunchSignup Hook
   ─────────────────────────────────
   File: packages/web/src/hooks/useLaunchSignup.ts
   
   New API:
   ```typescript
   interface SignupOptions {
     launchId: string;
     productId: string;  // NEW: Required for all signups
     mode: 'account' | 'public';
     email?: string;  // Required for public mode
   }
   
   signupForLaunch(options: SignupOptions): Promise<void>
   ```
   
   Modes:
   - account: Requires sign-in, stores userUid
   - public: Optional, email-only signups (if VITE_LAUNCH_SIGNUP_PUBLIC_ENABLED=true)
   
   Idempotency:
   - Document ID uses SHA-256 hash of email or uid
   - Prevents duplicate signups for same launch + user
   
   SHA-256 Implementation:
   ```typescript
   async function sha256(text: string): Promise<string> {
     const encoder = new TextEncoder();
     const data = encoder.encode(text);
     const hashBuffer = await crypto.subtle.digest('SHA-256', data);
     const hashArray = Array.from(new Uint8Array(hashBuffer));
     return hashArray.map(b => b.toString(16).padStart(2, '0')).join('');
   }
   ```
   
   Document Structure (Account Mode):
   ```json
   {
     "launchId": "launch_2025_q1_ropi_runner",
     "productId": "prod_ropi_runner_2025",
     "userUid": "abc123uid",
     "email": "user@example.com",
     "createdAt": Timestamp,
     "source": "aoss-web",
     "status": "active"
   }
   ```
   
   Document Structure (Public Mode):
   ```json
   {
     "launchId": "launch_2025_q1_ropi_runner",
     "productId": "prod_ropi_runner_2025",
     "userUid": null,
     "email": "public@example.com",
     "createdAt": Timestamp,
     "source": "public-form",
     "status": "active"
   }
   ```

3. Firestore Security Rules for Launch Signups
   ────────────────────────────────────────────────
   File: firestore.rules
   
   Updated Rules:
   ```
   match /launchSignups/{signupId} {
     // Account-based signup (requires auth)
     allow create: if (
                     request.auth != null
                     && request.resource.data.userUid == request.auth.uid
                     && request.resource.data.source == 'aoss-web'
                     && request.resource.data.keys().hasAll([
                       'launchId', 'productId', 'userUid', 
                       'createdAt', 'source', 'status'
                     ])
                     && request.resource.data.status == 'active'
                   )
                   // Public email signup (no auth required, if enabled)
                   || (
                     request.resource.data.userUid == null
                     && request.resource.data.source == 'public-form'
                     && request.resource.data.keys().hasAll([
                       'launchId', 'productId', 'email', 
                       'createdAt', 'source', 'status'
                     ])
                     && request.resource.data.status == 'active'
                   );
     
     // Allow users to read their own signups (account-based only)
     // Allow admins to read all signups
     allow read: if request.auth != null
                 && (
                   (isAdmin() || isAdminViaMetadata())
                   || resource.data.userUid == request.auth.uid
                 );
     
     // Allow users to cancel their own signups (change status to 'cancelled')
     // Allow admins to update any signup
     allow update: if request.auth != null
                   && (
                     (isAdmin() || isAdminViaMetadata())
                     || (
                       resource.data.userUid == request.auth.uid
                       && request.resource.data.status == 'cancelled'
                       && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['status'])
                     )
                   );
     
     // No deletes (signups are immutable, use status='cancelled' instead)
     allow delete: if false;
   }
   ```

NOTES
═══════════════════════════════════════════════════════════════════════════════

Admin Custom Claims:
- Users must sign out and sign back in for claims to take effect
- Token refresh happens automatically after 1 hour
- For immediate testing, use getIdTokenResult(true) to force refresh

Email Verification:
- Firebase automatically sends verification email on sign-up
- Verification link expires after 1 hour
- Resend email uses rate limiting (too many requests → error)

Launch Signups:
- SHA-256 hashing ensures consistent document IDs
- Idempotent: Repeated signups don't create duplicates
- Status='cancelled' allows soft deletes (no hard deletes)

Staging vs Production:
- Staging: Soft enforcement (warnings only, writes allowed)
- Production: Hard enforcement (writes blocked for unverified admins)
- Use VITE_ENV to control behavior

Public Signup Mode:
- Disabled by default
- Enable with VITE_LAUNCH_SIGNUP_PUBLIC_ENABLED=true
- Requires separate UI/route for public-facing forms
- Security: Public mode allows unauthenticated writes (use with caution)
