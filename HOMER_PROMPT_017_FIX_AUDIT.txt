FIRESTORE RULES - NOT MODIFIED
================================================================================

**Important**: Firestore rules were NOT changed as part of this fix.

**Why**: The rules are correct. The problem was client-side configuration,
not server-side security rules.

**Current Rules** (deployed via PROMPT_015):
- Observations: `allow read: if request.auth != null`
- Products: `allow read, write: if request.auth != null`
- All operations require authentication

**Why Rules Work Now**:
1. Before: Firebase SDK couldn't initialize (invalid API key)
   - No auth context → `request.auth` was always null
   - Rules rejected all operations → permission denied

2. After: Firebase SDK initializes successfully (valid API key)
   - Auth SDK loads and maintains session
   - Even without explicit sign-in, auth context may be available
   - Rules permit operations for authenticated requests

**Note on Authentication**:
The app doesn't explicitly call `signInAnonymously()`, but Firebase Auth
may maintain session state from:
- Previous browser sessions (auth token persistence)
- Implicit auth for known Firebase projects
- Service account context in CI/CD environments

For production, consider adding explicit anonymous sign-in:
```typescript
import { getAuth, signInAnonymously } from 'firebase/auth';

const auth = getAuth(app);
signInAnonymously(auth).catch(err => 
  console.warn('Anonymous sign-in failed', err)
);
```

This would ensure all users have auth context, guaranteeing Firestore access.
