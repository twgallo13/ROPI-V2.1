ARCHITECTURE DETAILS
================================================================================

Data Flow:
----------
1. CSV Upload → /api/import (POST multipart/form-data)
2. Admin Auth Check (Firebase Auth + custom claims)
3. Busboy parses file upload
4. PapaParse converts CSV → array of objects
5. For each row:
   - Source columns captured with line number
   - Normalization via column mappings
   - Validation with error/warning generation
   - Product ID derived from SKU
   - Row status determined (pending/failed)
6. Batch record created in import_batches/{batchId}
7. Rows saved in batches to import_batches/{batchId}/rows/*
8. Batch status updated to processed/failed
9. Response with summary (batchId, counts)

Import Engine Row Schema:
--------------------------
{
  rowId: string,              // UUID
  batchId: string,            // Batch UUID
  source: {
    columns: {...},           // Raw CSV key-value pairs
    lineNumber: number        // CSV line number
  },
  normalized: {
    sku: string,
    title: string,
    brand: string,
    // ... all mapped fields
  },
  validation: {
    isValid: boolean,
    errors: ValidationIssue[],
    warnings: ValidationIssue[]
  },
  meta: {
    rowId: string,
    batchId: string,
    productId: string,        // Derived from SKU
    importedAt: string,       // ISO timestamp
    importedBy: string,       // User ID
    status: 'pending' | 'processed' | 'failed',
    errorMessage?: string
  }
}

Column Mapping Example:
-----------------------
{
  sourceColumn: 'SKU',
  targetField: 'sku',
  required: true,
  transform: 'trim'
}

Transforms: trim, uppercase, lowercase, number, date, array

Validation Codes:
-----------------
- MISSING_REQUIRED_FIELD
- INVALID_FORMAT
- INVALID_VALUE
- OUT_OF_RANGE
- DUPLICATE_SKU
- INVALID_DATE
- INVALID_PRICE
- INVALID_QUANTITY
- UNMAPPED_FIELD
- NORMALIZATION_FAILED

NOTES & OBSERVATIONS
================================================================================

Implementation Decisions:
-------------------------
1. UUID for row/batch IDs instead of sequential numbers for distributed system
   compatibility and collision avoidance

2. Product ID derived from SKU via lowercase + hyphen normalization to ensure
   Firestore document ID compatibility and prevent case-sensitivity issues

3. Separate errors vs warnings to allow partial imports where non-critical
   issues don't block row processing

4. Firestore batched writes (500 rows per batch) to stay within limits and
   improve performance for large imports

5. PapaParse chosen for CSV parsing due to robust header handling, dynamic
   typing, and error reporting

6. Busboy for multipart/form-data parsing as it's the recommended approach
   for Firebase Functions file uploads

7. Express types used for middleware to maintain compatibility with Firebase
   Functions v1 (which wraps Express)

Known Limitations:
------------------
- No duplicate SKU detection across batches
- No support for custom column mappings (uses DEFAULT_COLUMN_MAPPINGS only)
- No support for GCS URL imports (only direct file upload)
- Max file size limited by Cloud Functions request size (10MB default)
- No progress tracking for large imports
- No rollback mechanism if batch processing fails mid-way

Performance Considerations:
---------------------------
- Large CSV files (>1000 rows) may hit Cloud Function timeout (60s default)
- Firestore write batching improves throughput but adds complexity
- Consider using Cloud Tasks for async processing of large imports
- Memory usage scales with CSV size (entire file loaded into memory)

Security Notes:
---------------
- Admin custom claim enforcement prevents privilege escalation
- No client-side writes to import_batches (server-only via Functions)
- Firestore rules provide defense-in-depth even if Function auth bypassed
- File uploads not sanitized for malicious content (CSV only, no execution)

Testing Coverage:
-----------------
- Normalization: Comprehensive (all transforms, edge cases)
- Validation: Comprehensive (errors, warnings, field relationships)
- Row building: Good (valid/invalid, empty rows, batching)
- Import service: Basic (parsing, stats) — needs expansion for error cases
- End-to-end: None yet — would require Firebase emulator + auth setup
