B. CI HARDENING WITH E2E TESTS
═══════════════════════════════════════════════════════════════════════════════

Workflow: .github/workflows/e2e-tests.yml

✅ Implementation:

1. E2E CI Job
   ───────────
   Triggers:
   - On pull_request (opened, synchronize, reopened)
   - Manual workflow_dispatch with custom base_url
   
   Steps:
   1. Checkout code
   2. Setup Node.js 20 + pnpm
   3. Install dependencies
   4. Install Playwright browsers (chromium)
   5. Wait for preview deployment (60s delay)
   6. Determine test URL:
      - PR: https://ropi-bccee--pr-{PR_NUM}-aoss-staging.web.app
      - Manual: Custom BASE_URL input
      - Default: https://ropi-aoss-staging.web.app
   7. Wait for deployment to be ready (health check with curl)
   8. Run E2E tests with BASE_URL env var
   9. Upload Playwright report artifacts
   10. Comment on PR with results

2. Merge Gating
   ─────────────
   Required Status Check: `e2e`
   
   To Enable in GitHub:
   1. Go to Settings → Branches → aoss-main
   2. Edit branch protection rule
   3. Add "e2e" to required status checks
   4. Save changes
   
   Result: PRs cannot merge unless E2E tests pass on preview URL

3. Test URL Strategy
   ──────────────────
   - Preview Channel Format: pr-{PR_NUMBER}
   - Firebase generates preview URLs automatically
   - E2E waits for deployment + health check before running
   - Max wait time: 2 minutes (24 × 5-second attempts)

4. Artifacts
   ──────────
   On test failure:
   - Playwright HTML report (retention: 7 days)
   - Screenshots (only-on-failure)
   - Videos (retain-on-failure)
   - Test results JSON

C. CLIENT-SIDE ERROR MONITORING (SENTRY)
═══════════════════════════════════════════════════════════════════════════════

Library: @sentry/react, @sentry/vite-plugin

✅ Implementation:

1. Sentry Initialization
   ──────────────────────
   File: packages/web/src/monitoring/sentry.ts
   
   initSentry() function:
   - Requires VITE_SENTRY_DSN environment variable
   - Sets environment (staging | production)
   - Sets release version (VITE_APP_VERSION or 'dev')
   - Integrations:
     * browserTracingIntegration() for performance
     * replayIntegration() for session replay (privacy-preserving)
   
   Sampling Rates:
   - Production: 10% traces, 10% replays (cost-effective)
   - Staging: 100% traces, 100% replays (full visibility)
   - Replay on Error: 100% (always capture errors)
   
   Privacy:
   - maskAllText: true (redacts PII in session replays)
   - blockAllMedia: true (no images/videos in replays)
   - Scrub Authorization & Cookie headers before send

2. Error Capture Functions
   ────────────────────────
   captureAuthError(error, context):
   - Tag: feature:auth
   - Used in: AuthProvider (sign-in/sign-up failures)
   
   captureFirestoreError(error, context):
   - Tag: feature:firestore
   - Used in: useLaunchSignup (permission-denied errors)
   
   captureLaunchSignupError(error, context):
   - Tag: feature:launch-signup
   - Used in: useLaunchSignup (signup failures)
   
   captureObservationError(error, context):
   - Tag: feature:observations
   - Available for observations.ts (future integration)

3. Breadcrumb Tracking
   ────────────────────
   addRouteBreadcrumb(route):
   - Category: navigation
   - Tracks user navigation through app
   
   addActionBreadcrumb(action, data):
   - Category: action
   - Tracks key user actions:
     * launch_signup_submitted
     * observation_created
     * observation_resolved
   
   Usage:
   - Added to useLaunchSignup on successful signup
   - Available for observations service (future)

4. User Context
   ─────────────
   setSentryUser(userId, email):
   - Called in AuthProvider when user signs in
   - Associates errors with specific users
   
   clearSentryUser():
   - Called in AuthProvider on sign-out
   - Clears user context for privacy

5. Integration Points
   ───────────────────
   main.tsx:
   - Call initSentry() at app bootstrap
   
   AuthProvider.tsx:
   - Set user context on auth state change
   - Capture errors in sign-in/sign-up methods
   
   useLaunchSignup.ts:
   - Capture launch signup errors
   - Distinguish permission errors (Firestore) vs general errors
   - Add breadcrumbs on successful signup

6. Environment Variables
   ──────────────────────
   VITE_SENTRY_DSN: Sentry project DSN (required)
   VITE_APP_VERSION: Release version (optional, defaults to 'dev')
   VITE_ENV: Environment name (staging | production)

2. Production Rollout Plan
   ────────────────────────
   Phase 1: Internal Testing (Day 1)
   - Audience: 2-3 admin test accounts
   - Duration: 24 hours
   - Goals: Verify auth, admin claims, email verification, launch signups
   - Go/No-Go: No critical Sentry errors, all test accounts working
   
   Phase 2: Limited Internal Users (Day 2-3)
   - Audience: 10-15 internal users (merchandising, buyers, photographers)
   - Duration: 48 hours
   - Goals: Real workflows, performance under light load, user feedback
   - Go/No-Go: No data loss, acceptable performance, positive feedback
   
   Phase 3: Full Internal Rollout (Day 4+)
   - Audience: All internal users (~50-100)
   - Duration: Ongoing
   - Goals: Full production usage, continuous monitoring
   - Success Metrics: 95%+ uptime, < 5% error rate, user satisfaction > 4/5

3. Rollback Procedures
   ────────────────────
   Scenario 1: Critical Bug
   - Firebase Hosting rollback: `firebase hosting:rollback`
   - Timeline: < 5 minutes
   
   Scenario 2: Firestore Rules Permission Errors
   - Checkout previous rules: `git checkout HEAD~1 -- firestore.rules`
   - Deploy: `firebase deploy --only firestore:rules`
   - Timeline: < 5 minutes
   
   Scenario 3: Performance Degradation
   - Check Firebase Console metrics
   - Identify bottleneck (Firestore queries, hosting bandwidth)
   - Mitigate or rollback
   - Timeline: Evaluate (1-2 hours)
   
   Rollback Decision Matrix:
   - Critical (all users blocked): ✅ Rollback immediately (< 5 min)
   - High (major features broken): ✅ Rollback within 30 min
   - Medium (non-critical broken): ⚠️ Evaluate (1-2 hours)
   - Low (UI glitch): ❌ Fix forward

4. Feature Flags
   ──────────────
   VITE_ENV: production | staging
   - Controls email verification enforcement (hard vs soft)
   
   VITE_LAUNCH_SIGNUP_PUBLIC_ENABLED: true | false
   - Enables public email signup mode (default: false)
   
   VITE_SENTRY_DSN: https://...@sentry.io/...
   - Required for error monitoring
   
   Disabling Features:
   - To disable public signups: Set VITE_LAUNCH_SIGNUP_PUBLIC_ENABLED=false, rebuild, redeploy

5. Monitoring
   ───────────
   Sentry Dashboard: https://sentry.io/organizations/ropi-aoss/projects/
   - Alert Thresholds:
     * Auth errors: > 10/hour
     * Firestore errors: > 20/hour
     * Launch signup errors: > 5/hour
     * Observation errors: > 10/hour
   
   Firebase Console: https://console.firebase.google.com/project/ropi-bccee
   - Key Metrics:
     * Hosting bandwidth, cache hit rate
     * Firestore read/write operations
     * Auth daily active users
